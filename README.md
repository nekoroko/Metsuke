# AI Agent Studio

ローカルLLM（LM Studio）または任意のAPIで動く、自律型タスク実行エージェント基盤。
Web GUIからツールを作成・管理し、スケジュール実行できます。

データを外部に送らず、自分のPC上で完結させたい人向けに作っています。

## 構成

このプロジェクトは2つのリポジトリで構成されています。

```
agent-project/   ReActエージェントのコア（LLM呼び出し、ツール、レビュアー）
agent-studio/    Web GUI（Streamlit）、DB、スケジューラ
```

`agent-studio` は `sys.path` 経由で `agent-project` を読み込んで動きます。
`agent-project` 単体でもCLIから直接エージェントを動かせます（`run.py`）。

## 動作要件

### 必須
- Python 3.12以上
- LM Studio（ローカルLLMを使う場合）、またはOpenAI互換API（Bedrock/OpenAI等)のエンドポイント
- Podman（**必須**。ツール・エージェントのコード実行はすべてコンテナ内で行われます）

### 推奨スペック（ローカルLLM利用時）
- VRAM: 8GB以上
- **Context Length: 8192トークン以上を推奨**
- モデルサイズ: 8B〜12B程度（Instruction Tuned版、末尾に `-it` が付くもの）

### Context Lengthが8192未満の環境について

4096トークンでも動作しますが、Thinking/Reasoning機能を持つモデルや、
複数ステップにまたがる複雑なタスクでは、トークン予算が不足して
応答が途中で打ち切られやすくなります。

これに対して以下の耐性機構を実装済みです。動かなくなることは避けられますが、
快適に使うには8192以上のContext Lengthを推奨します。

- **自動継続**: 応答がトークン上限で切れた場合、続きを自動的に追加取得して結合する
- **ステップ予算に応じた収束制御**: 残りステップ数が少なくなると、新規調査を控えて
  今ある情報をまとめる方向に自動で誘導する
- **強制収束**: それでもステップ上限に達した場合、今までの情報だけで
  簡潔な回答を1回だけ強制的に生成し、エラー落ちを防ぐ
- **Thinking検知と予算調整**: Reasoning機能を無効化できないモデル/設定でも、
  実際にThinkingが行われたことを検知し、以降のトークン予算・継続回数を自動的に広げる

## セットアップ

### 1. agent-project

```bash
cd agent-project
python3 -m venv .venv
source .venv/bin/activate   # Windowsは .venv\Scripts\activate
pip install -r requirements.txt
```

### 2. agent-studio

```bash
cd agent-studio
source ../agent-project/.venv/bin/activate  # venvは共有してOK
pip install -r requirements.txt
streamlit run app.py
```

ブラウザで `http://localhost:8501` を開きます。

### 3. サンドボックスイメージ（事前準備は不要）

AI生成コードのプレビュー実行には専用のコンテナイメージを使いますが、
**手動でビルドする必要はありません**。初回のプレビュー実行時に自動でビルドされます
（数分かかります。このときだけネットワークが必要です）。

素の `python:3.12-slim` には標準ライブラリしか入っていないため、専用イメージが
無いと pandas / requests / ddgs 等を使うツールは `ModuleNotFoundError` になります
（サンドボックスは通信を遮断するので、コンテナ内での `pip install` もできません）。

事前にビルドしておきたい場合は、以下を実行しても構いません。

```bash
podman build -t agent-studio-sandbox:latest .
```

自前で用意したイメージを使う場合は、環境変数 `AGENT_SANDBOX_IMAGE` で指定します。
その場合は自動ビルドの対象外になり、イメージの管理は利用者側の責任になります。

### 4. LLM接続設定

起動後、「⚙️ 設定」タブから接続先を設定してください。

- **ローカルLLM（デフォルト）**: Base URL・モデル名を指定
- **API**: プロバイダ種別を選んで接続
  - **OpenAI互換エンドポイント**: OpenAI本家、AWS Bedrock（Access Gateway経由）、Google Gemini、LiteLLM Proxy等
  - **Anthropic（ネイティブ）**: `langchain-anthropic` 経由でClaude APIに直接接続。
    OpenAI互換レイヤーはAnthropic公式が「本番用途には非推奨」としているため、
    Extended Thinking等の機能をフルに使うにはこちらを推奨

設定は `agent_studio.db` に保存され、`agent-project` 側もこのDBを
参照するため、一度設定すれば両方に反映されます。

DBの場所は `paths.py` で一元管理しており、実行時のカレントディレクトリに
依存しません（`paths.py` と同じディレクトリに置かれます）。
`agent-project` と `agent-studio` を別ディレクトリに分けて運用する場合は、
環境変数 `AGENT_STUDIO_DB` で明示的にパスを指定してください。

#### ローカルLLMサーバーの選択肢

LM Studioでの動作を主に検証していますが、OpenAI互換APIを持つ推論サーバーであれば
理論上は他のものでも動作するはずです（LM Studio以外は未検証）。

| サーバー | 特徴 |
|---|---|
| **LM Studio** | GUI操作でモデル管理・ロード設定ができる。本プロジェクトの検証環境 |
| **Ollama** | セットアップが最も簡単（`ollama serve`のみ）。単一ユーザー向け |
| **vLLM** | 高スループット。複数ユーザーでの同時利用を想定するならこちら |
| **llama.cpp（サーバー単体）** | 依存が少なく軽量。エッジ環境向け |

切り替える場合は「⚙️ 設定」のBase URLを対象サーバーのエンドポイント
（例: Ollamaなら `http://localhost:11434/v1`）に変更するだけです。

#### 最大出力トークン数（max_tokens）について

接続先がローカルかAPIかに関わらず、実際の上限は環境ごとに異なります
（ローカルはサーバー側のContext Length設定次第、APIはモデル・プロバイダ次第）。
「APIだから大きい値で決め打ち」「ローカルだから小さい値で決め打ち」という
実装は、環境によって不正確になりズレます（実際、この決め打ちが原因で
長文レポートが途中で打ち切られる不具合が発生したことがあります）。

そのため本アプリでは、Local / OpenAI互換API / Anthropic のいずれの設定画面にも
「最大出力トークン数」の入力欄と「🔌 接続テスト（自動取得を試す）」ボタンを
共通で用意しています。

- **接続テストの成功率はプロバイダ次第**です。Anthropicは公式Models APIで
  確実に取得できます。それ以外（ローカルサーバー、OpenAI互換API全般）は
  実装によって対応状況がまちまちで、多くの場合は失敗します
  （標準のOpenAI API仕様には含まれない情報のため）。
- **自動取得に失敗した場合は手入力してください。** ローカルならサーバー側の
  設定画面（例: LM Studioの「Load」タブのContext Length）を確認、
  APIなら各プロバイダのドキュメントを確認してください。
- 値は「⚙️ 設定」タブで保存した内容がそのまま使われます。
  未設定の場合のみ、コード内の保守的な既定値（ローカル: 1500 / API: 4000）に
  フォールバックします。

### 5. 検索プロバイダ設定（任意）

デフォルトはAPIキー不要のDuckDuckGoです。精度を上げたい場合は
「⚙️ 設定」タブからTavily / Google Custom Search / Brave Searchの
APIキーを設定できます（未設定時は自動的にDuckDuckGoにフォールバックします）。

なお、Google Custom Search JSON APIは2026年時点で新規顧客の受付を終了しています。
既存のプログラム可能検索エンジンをお持ちの方以外は、Tavily または Brave Search を
推奨します。

## 使い方

### Type 1: ツール（固定処理、LLM不要で実行）

「🤖 ツール作成」タブでAIにツールを作らせます。ファイル集計、ログ解析など
毎回同じ処理をするタスクに向いています。

1. やりたいことを自然言語で入力 → AIがPythonコードを生成
2. Podmanサンドボックスでプレビュー実行して安全性を確認
3. エラーが出た場合は「AIに修正させる」ボタンで自動修正
4. コードレビュー・セキュリティレビューを自動実行
5. 「検証済み」として保存すると、手動実行・スケジュール実行の対象になる
   （実行環境はプレビュー時と同じサンドボックスなので、挙動は変わりません）

### Type 2: エージェント（動的判断、LLMが自律実行）

「🧠 エージェント」タブで、調査・要約・判断が必要なタスクを登録します。
毎回LLMが状況を見て判断するため、Type 1では対応できないタスク
（最新ニュースの調査、異常検知後の深掘り等）に向いています。

エージェントタスクには、使用可能なType1ツールを紐付けられます。
「ログを収集するツール」＋「収集結果を分析するエージェント」のような
組み合わせワークフローが組めます。

### スケジュール実行

Type1/Type2どちらのタスクも、cron式で定期実行を登録できます。
実行はバックグラウンドジョブとして投入されるため、ブラウザを閉じても
処理は継続します。「📋 実行履歴」タブで進捗・結果を確認できます。

## アーキテクチャの要点

### ReActループ + Critic（専門家レビュアープール）

エージェントは以下のループで動作します。

```
react（ツール実行・思考） → DONE
                              ↓
                        Dispatcher（タスク内容からレビュアーを選定）
                              ↓
              fact_checker / code_reviewer / security_reviewer /
              data_analyst / generic_reviewer
                              ↓
                   OK → 終了 ／ 要修正 → react に戻る（最大2回）
```

Criticはエージェント本体とは別のLLM呼び出しで、成果物を批判的にレビューします。
同じLLMが自分の回答を自己採点するより、役割を分離した方が問題を見つけやすいためです。

### サンドボックス実行

**コードを実行する経路はすべてPodmanコンテナ内で動きます。**
検証済みツールも例外ではありません。

すべての実行に共通してかかる制限:

- ルートFS読み取り専用（`--read-only`）、`/tmp` のみtmpfsで書き込み可
- 見えるファイルは作業ディレクトリと、明示的に設定した追加マウントのみ
- メモリ512MB / プロセス数32 / CPU 1コア
- 使い捨てコンテナ（`--rm`）で、実行後には何も残らない

経路ごとの権限は `sandbox.py` の PROFILE_* に集約しています。

| 実行経路 | 通信 | 作業ディレクトリ | タイムアウト |
|---|---|---|---|
| 検証済みツール（UI実行・スケジュール実行・エージェントからの呼び出し） | 許可 | 書き込み可 | 120秒 |
| プレビュー実行 | 画面のチェックボックス | 画面のチェックボックス | 60秒 |
| エージェントの `generate_code` | 遮断 | 読み取り専用 | 60秒 |
| エージェントの `run_shell` | 遮断 | 書き込み可 | 30秒 |

検証済みツールに通信を許可しているのは、人間のレビューを通過しているためです。
一方、エージェントが実行時に組み立てるコード・コマンドはレビューを経ていないため
通信を遮断しています（調査が必要な場合は `web_search` / `fetch_url` を使わせます）。

以前は「検証済みツールはホスト直接実行」「`run_shell` も隔離なし」でしたが、
以下の理由で全経路をサンドボックス化しました。

- プレビューと本番の実行環境が一致し、「プレビューは通ったのに本番で落ちる」
  が構造的に消える
- 人間のレビューは万能ではなく、検証済みコードにもバグはあり得る
  （パス誤りによる削除など）ため、爆発半径を限定する価値がある
- `run_shell` だけがホスト直接実行だと、エージェントが `generate_code` の
  隔離をそこから回避できてしまう

APIキーが必要な場合は、設定DBをマウントするのではなく、検索APIキーだけを
環境変数として個別に注入しています（LLMのAPIキーは渡しません）。DBには
両方が平文で同居しているため、DBごと渡すと実行コードに全プロバイダのキーを
晒すことになります。

#### この構成でできなくなること

**ホストのシステム情報は取得できません。** コンテナ内から見えるディスク使用量・
メモリ量・CPU数・プロセス一覧は、いずれもコンテナ自身の値です。エラーにならず
「もっともらしい別の数値」が返るため、CREATOR_PROMPT側でこの種のツールを
生成しないよう明示し、要望された場合は NOT_SUITABLE を返すようにしています。

**作業ディレクトリ以外のホストファイルには、マウント設定が必要です。**
「⚙️ 設定」タブの「サンドボックスのファイルアクセス」から指定できます。

```
/var/log:/var/log:ro
/home/user/data:/data:ro
```

設定は全実行経路に共通で適用されます。ツールごとに設定を分けていないのは、
経路ごとに権限がバラつくのを避けるためです。

**Podmanが全実行の必須依存になります。** Podmanが動かない状態では、
スケジュール実行を含めてツールが実行できなくなります。

### ツールとサブタスクの権限管理

エージェントタスクには、使用可能なType1ツールを明示的に紐付けます（許可リスト方式）。
これにより、AIが「何でも自由に呼べる」状態を避け、実行コストと影響範囲を
予測可能にしています。

### ツールが使えるライブラリを増やす / 減らす

「⚙️ 設定」タブの **「ツール実行時ライブラリ」** セクションから操作できます。

- 定義を編集して保存（1行1パッケージ。行末の `# ...` はAIへの説明文になる）
- AIに提示される許可リストのプレビュー
- サンドボックスイメージの状態表示と、その場での再ビルド

```
ddgs             # DuckDuckGo検索
beautifulsoup4   # HTML解析、bs4としてimport
pandas>=2.0      # バージョン指定も書ける
```

UIが編集しているのは `requirements-tools.txt` そのもので、設定DBには保存されません。
`Containerfile` が実ファイルを読む以上、DBに持たせると定義元が二重化するためです。
ファイルを直接編集しても同じように動きます。

| 反映先 | 反映のされ方 |
|---|---|
| AIに提示する許可リスト | プロンプト生成時に毎回読み込むため即時 |
| サンドボックスイメージ | 次回の実行時に自動で再ビルド |

再ビルドの要否は、ファイルの内容ハッシュをイメージのラベルに焼き込んで判定して
います。そのため「ライブラリを足したのに再ビルドを忘れて古いイメージで動く」
ことは起きません（説明文だけを直した場合は再ビルドされません）。

ツールコードはすべてコンテナ内で実行されるため、ここで定義したライブラリを
ホスト側にインストールする必要はありません。

なお、**AIが自分でライブラリを追加することはできません**。これは意図的な設計です。
AI生成コードが実行時に依存を増やせるということは、AI自身がサプライチェーンに
手を出せるということであり、ネットワーク遮断やセキュリティレビューで守ろうと
しているものが崩れます。許可リストの拡張は、人間が明示的に判断すべき
ポリシー変更として扱っています。

## 既知の制約

- Windowsネイティブでの動作は現時点で未検証です（WSL2上での利用を推奨）。
  Podman自体はWindows上でLinuxコンテナを起動できるため、大きな障害にはなりません。
- 検索の精度はDuckDuckGo利用時は限定的です。重要な調査タスクでは
  Tavily等のAPIキー設定を推奨します。
- ローカルLLMの推論品質は、モデルサイズ・量子化レベルに強く依存します。
  複雑な判断・重要度の取捨選択が必要なタスクは、大きいモデルやAPI
  （Claude/GPT等）の方が精度が高くなる傾向があります。

## ディレクトリ構成

```
agent-project/
  config.py       LLM接続設定（Local/API切り替え）
  state.py        エージェントの状態定義 + 初期状態ファクトリ
  tools.py        エージェントが使うツール群
  graph.py        ReActループ + Criticのグラフ定義
  reviewers.py     専門家レビュアープール
  sandbox.py      Podmanサンドボックス実行
  run.py          CLIから直接実行する場合のエントリポイント

agent-studio/
  config.py       LLM接続設定（agent-projectと同一内容）
  db.py           SQLite（ツール、タスク、スケジュール、実行履歴、設定）
  executor.py     ツール実行・エージェント実行（バックグラウンド対応）
  ai_creator.py   AIによるツール生成・エラー修正
  scheduler.py    APSchedulerによる定期実行
  app.py          Streamlit UI

共通/
  paths.py                設定DBの場所を一元管理（唯一の定義箇所）
  settings_store.py       設定DBの読み取り（config/tools/sandboxが共用）
  tool_runtime.py         ライブラリ定義の読み書き・プロンプト生成・ハッシュ
  Containerfile           サンドボックス実行用イメージの定義
  requirements-tools.txt  AI生成ツールが使えるライブラリの唯一の定義
```
