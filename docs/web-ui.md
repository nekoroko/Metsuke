# React Web UI — 実装メモ

デザイン指示書（`design_handoff_react_webui/README.md`）に沿って、Streamlit UI を
React SPA ＋ FastAPI に置き換えたときの判断を残す。指示書そのものは配布物なので、
ここには「なぜそう作ったか」だけを書く。

## 構成

```
api/     FastAPI。既存の db / executor / scheduler / graphs / llm_profiles を薄く包む
web/     Vite + React 18 + TypeScript。styles.css（Modernist）をそのまま使う
app_streamlit.py   旧UI。同じDBを見るので、移行中は両方立ち上げて比べられる
```

配信は1プロセス。`vite build` の成果物を FastAPI の StaticFiles が配る
（`python -m api` → `http://localhost:8000`）。開発時だけ Vite dev server を
別に立て、`/api` を 8000 へプロキシする。

## ロジックをフロントに持たせない

`THOUGHT:` / `ACTION:` / `DONE:` のパースは `executor.parse_history_for_display`
のまま。API が `steps` として整形済みの配列を返し、フロントは表示するだけにした。

同じ正規表現をフロントにも書くと、**片方だけ直す事故**が起きる。実行の見え方が
Streamlit 版とズレると、移行中にどちらが正しいのか判断できなくなる。
`graph_label` / `model_label` も同じ理由でサーバ側で作っている。

## APIキーを外へ出さない

- `GET /api/llm-profiles` は `api_key` を返さない。`has_api_key`（真偽値）だけ。
- `GET /api/settings` は `*_api_key` を `********` に置き換える。
- `PATCH /api/llm-profiles/{id}` に**空文字の api_key が来たら無視する**。
  画面は鍵の実値を持っていないので、入力欄が空のまま保存されると鍵が消える。
- `PUT /api/settings` に伏せ字がそのまま返ってきた場合も無視する。

一度でも返すと devtools・プロキシログ・画面キャプチャに残り、あとから消せない。
`tests/test_api.py::TestLlmProfilesApi` が、作成・一覧・更新の3経路で固定している。

## 実行の追従は SSE、ポーリングはしない

エージェント実行は APScheduler のジョブとして走り、進捗を
`update_execution_progress` でDBへ書く。API のハンドラはその外側にいるので
generator を直接受け取れない。`api/events.py` がDBを1秒ごとに見て、
history / trace の**件数差分**だけを送る。

件数で持つのは、同じイベントを二度送らないため。再接続時はサーバが履歴を頭から
流し直すので、**ページを離れて戻っても復元できる**（クライアント側に復元処理は無い）。

ツール生成（`ai_creator`）は同一プロセスの generator なので、そちらは
ワーカースレッド経由で yield をそのまま流す（LLM呼び出しでイベントループを
止めないため）。

## 自動スクロールは末尾にいるときだけ

タイムラインは、ユーザーが上を読んでいる間は動かさない。`scrollIntoView` は使わず、
スクロール位置が末尾から40px以内のときだけ `scrollTop` を更新する。
新しいトークンが来るたびに視点が飛ぶと、流れているログは読めない。

## デザインシステムの守り方

`web/src/styles/modernist.css` がトークンの正。画面固有CSS（`app.css`）でも
hex・フォント名・角丸を直に書かない。指示書 §8 の確定値（サイドバー212px、
右パネル392px、区切り2px/行1px 等）は `app.css` に集約してある。

- 角丸は全て 0（`--radius-*: 0px`）
- `:focus-visible` は 2px のアクセント。ブラウザ既定の青は出さない
- アニメーションは 120–160ms の opacity/transform のみ

## 停止（cancel）の限界

`POST /api/executions/{id}/cancel` は、APScheduler のジョブがまだ始まっていなければ
取り消す。走り出したグラフには割り込めないので、状態を error にして画面と履歴の上では
終わったことにする。ワーカーは現在のステップを終えてから `finish_execution` を
呼ぶが、そのときには既に終了済みなので実害はない。

**「実行中のグラフを本当に止める」ことは今の設計ではできない。** やるなら
`AgentState` に停止フラグを持たせ、各ノードの入口で見る必要がある（未着手）。

## デザインシステムのクラス名を借りるときの注意

サイドバーに `.nav` / `.nav-item` を使ったところ、**選択中の項目が消えた**。

modernist.css の `.nav` は「ヘッダーバー」用の別コンポーネントで、

```css
.nav a:hover, .nav a[aria-current='page'] { color: var(--color-accent); }
```

を持っている。`NavLink` は選択中のリンクに `aria-current="page"` を付けるので、
`.nav a[aria-current='page']`（詳細度 0,2,1）が `.nav-item.active`（0,2,0）に勝ち、
**赤背景の上に赤文字**になっていた。

詳細度で殴り返すのではなく、`.sidenav-*` に名前を分けた。`.nav` は
デザインシステム側では別のものを指しているので、そもそも借りるのが誤りだった。

**用途が違うなら名前も分けること。** クラス名を再利用すると、
今は見えていない指定まで一緒に付いてくる。

## ヘルプは画面の中に置く

`web/src/help/topics.ts` に Markdown で持ち、`/help/:topic` で出す。
README に飛ばさないのは、「Podman 未構築」と出ている人が知りたいのは
**その場での直し方**であって、リポジトリの構成説明ではないため。

サイドバーの状態タグ（検索プロバイダ / Podman）は、それぞれの
ヘルプへのリンクにしてある。表示から1クリックで手順に着く。

ヘルプの冒頭には `GET /api/meta` の現在値を出す（Podman の state、既定モデル、
検索プロバイダ）。手順だけ読んでも「自分がどれに当てはまるか」が分からない。

## 実行詳細のレイアウト

ヘッダーは固定、中身は3つの枠が独立してスクロールする。

```
+------------------------------------------+
| (1) ヘッダー（固定）                       |
+--------------------+---------------------+
| (4) 最終結果        | (3) Critic / Budget |  <- スクロールなし
| （スクロール）       +---------------------+
|                    | (2) タイムライン      |  <- スクロール
+--------------------+---------------------+
                     ^ ドラッグで左右の幅を変える
```

外側（`.main-scroll`）に任せるとヘッダーごと流れてしまうので、
`.run-page` に `height:100%` を与えてページ内で高さを確定させ、内側の枠に
`overflow:auto` を持たせている。`.main-scroll` は flex アイテムとして
高さが確定しているので、`%` 指定が効く。

## 作成の導線

エージェントタスクの新規作成画面を最初の実装で作り忘れていた。
`POST /api/agent-tasks` はあるのに、それを呼ぶ画面がどこにも無かった
（ライブラリにあるのは**ツール**の作成で、別物）。

`/tasks/new` を追加し、編集画面（`TaskDetailPage`）を `isNew` で兼用する。
入力する項目が編集時と同じなので、画面を分ける理由がない。

ルートは `:taskId` より**前**に置く。後ろだと `new` がIDとして解釈され、
「見つかりません」になる。

導線は3つ。タスク一覧のヘッダー、一覧が空のときの案内、⌘K で
一致が無かったとき。**ツールとエージェントは作る場所が違う**ので、
空状態では両方への入口を並べて出す。

## 上部を固定する

一覧のある画面（タスク・実行履歴・設定›モデル）は、**見出し・フィルタ行・
検索欄・テーブルの列見出しまでを固定**し、行だけがスクロールする。

```
<div className="page">          height:100% の縦フレックス
  <header className="page-header" />   flex:none
  <div className="filters" />          flex:none
  <div className="searchbar" />        flex:none
  <div className="page-scroll">        flex:1; overflow:auto
    <table>  ← thead th は position:sticky; top:0
```

**sticky を段に積む方法は取らない。** 2段目以降に `top` の実値が要るが、
見出しの高さは可変（`.roomy` で 26px→34px）で、当て推量を置くと条件次第で
隙間や重なりが出る。

一覧を持たない画面（ライブラリ・スケジュール・設定の他の節・ヘルプ）は
`.page-header` の `position: sticky; top: 0` だけで足りる。

**共通の器（`.main-scroll`）は変えない。** 高さを確定させるのは
そのページの中だけにする（下記の事故を繰り返さないため）。

**`.main-scroll` を flex column にしてはいけない。** 一度そうしたところ、
flex の子は既定で縮む（`flex-shrink:1`）ため、実行詳細**以外**の全ページで
ヘッダー・フィルタ行・テーブルが押し潰されて重なった。高さを埋めたいのは
実行詳細だけなので、共通の器を変えるのではなくそのページ側で解決する。

左右の幅は `SplitPane` で変えられる。幅は localStorage に残す
（実行を開くたびに動かし直すのは手間なので）。マウス専用にせず、
矢印キーと Home（既定に戻す）でも動かせる。

## SSE の再接続で同じステップが積み上がっていた

実測で **STEP 130 / 10** という表示になった。EventSource は接続が切れると
自動で再接続し、サーバは毎回**履歴を頭から流し直す**。受け側が append
していたため、再接続のたびに全履歴が積み増されていた。

`onopen`（再接続のたびに発火する）で受け側を空にする。サーバ側は
冪等のままでよく、クライアントが「この接続で来たものが全部」と
扱えばよい。クライアントのコメントには「重複を潰す」と書いてあったが、
実装していなかった。

## ステップ上限を画面で決め打ちしない

同じ画面で `maxSteps = 12` と書いていたが、実際の上限はグラフごとに違う
（ReAct 10 / リサーチ 18）。`GET /api/executions/{id}` が `max_steps` を
返すようにした。値は `graphs.make_state(kind, "")` から取るので、
予算の定義を変えても画面が追随する。

## この環境で確認したこと / していないこと

確認済み:

- `npm run build` が通り、`python -m api` で SPA とAPIが同一オリジンで配れること
- SPA のディープリンク（`/runs/xxx` を直接開く）が index.html を返すこと
- タスク作成 → 実行投入 → `graph_kind` と `llm_info` の記録 → 実行詳細の取得
- SSE が `text/event-stream` で `status` イベントを即時に返すこと
- `tests/test_api.py`（32件）

未確認:

- **ブラウザでの実際の表示**。ヘッドレス環境なので、レイアウト崩れや
  キーボード操作（⌘K / ⌘E / ⌘M）の挙動は目視できていない。
- LLM を実際に呼ぶ経路（ローカルLLMがこの環境から見えない）。
  タイムラインにステップが流れる様子は、実機で確認が要る。

## APIキーの置き方（平文のまま守る）

暗号化はしない。復号する鍵をどこかに平文で置くことになり、パスフレーズ方式に
すると定期実行が動かなくなる。**見かけ上の安全と引き換えに機能を失うだけ**なので、
平文のまま「置き場所・権限・持ち出し経路」で守る。AWS CLI / gh CLI / npm と同じ方針。

| 対策 | 実装 |
|---|---|
| パーミッション 0600 | `paths.secure_db_file()`。`init_db` から呼ぶ。WAL / journal も対象 |
| リポジトリの外に置く | `~/.local/share/agent-studio/agent_studio.db`。旧位置にあれば起動時に**移動**する |
| マウント禁止 | `sandbox.exposes_secrets()` が DB を見せる指定を落とす。親ディレクトリ指定も含む |
| 却下の可視化 | `POST /api/settings/check-mounts`。黙って落とすと「書いたのに効かない」になる |

### なぜ移動（コピーではない）か

両方に残ると、どちらが使われているのか分からない状態になる。旧位置に残骸が
あると、リポジトリを配った先に鍵が混ざる事故にもつながる。

### なぜマウントを止めるのか

サンドボックスの中で動くのは**AIが生成したコード**。DBが見える状態にすると
「生成コードが鍵を読んで外へ送る」経路が開く。ネットワークを許可した実行なら
そのまま持ち出せる。親ディレクトリを指定した場合も同じなので、
`os.path.commonpath` で前方一致を見る（文字列の `startswith` は区切りを誤る）。

### 守れないこと

- **同一ユーザーからは守れない。** 0600 は他ユーザーに対する防御であって、
  同じアカウントで動くプロセスからは読める
- 鍵が漏れた場合、こちらの設定を消しても無効にはならない。**プロバイダ側での
  失効が先**

## サービス名（Metsuke）の置き場所

表示名は `web/src/brand.ts` が唯一の定義箇所。旧名（AI Agent Studio）は
Shell / index.html / README / FastAPI の title に散っていて、名前を変えるときに
必ず取りこぼす形だった。文字列をベタ書きせず、必ずここから読む。

| 場所 | どう出しているか |
|---|---|
| サイドバー左上 | `BRAND_NAME_UPPER` ＋ `BRAND_TAGLINE`。クリックで `/help/about` |
| タブのタイトル | `App.tsx` が `pageTitle()` で `document.title` を上書き |
| `web/index.html` | 初回描画までの暫定表示。上書き前の一瞬だけ見える |
| ヘルプ | `help/topics.ts` の `about`（ヘルプの先頭）。`BRAND_NAME` を埋め込む |

### 内部識別子は変えていない

`agent_studio.db` / `AGENT_STUDIO_DB` / `~/.local/share/agent-studio/` /
`agent-studio-sandbox:latest` / Python のモジュール名は旧名のまま。

変えると、すでに動いている環境の設定・タスク・実行履歴が見つからなくなる。
DBは直前に「旧位置から新位置へ**移動**する」処理を入れたばかりで、ファイル名まで
変えると移行が二重になる（旧パス旧名 → 新パス旧名 → 新パス新名）。
イメージ名を変えれば全員が再ビルド（数分）からやり直しになる。

名前の変更で失うものが「表示が古い」だけなのに対し、内部識別子の変更で失うのは
利用者の保存データへの到達性なので、釣り合っていない。将来変えるなら、
旧名を読んで新名へ書き写す移行処理を先に用意すること。この理由は
ヘルプの `about` にも書いてあるので、片方だけ直すとズレる。

## 所要時間とトークンの計測

### 計測点は2つだけ

エージェント実行中の `llm.invoke` は `config.invoke_with_retry` しか通らない
（`invoke_with_continuation` も内部でこれを呼ぶ）。ノードの出入りは
`graph._with_trace` が全部通る。したがって各ノードの実装には手を入れていない。

| 何を | どこで |
|---|---|
| LLMの所要時間・トークン | `config.invoke_with_retry` → `metrics.record_llm` |
| ノードの入口 | `graph.measured`（`workflow.add_node` の登録時に包む） |
| ノードの出口・記録 | `graph._with_trace` → `metrics.take_node` |
| 実行スコープ | `executor._agent_steps`（3経路の共通の通り道）と `verify_run.run_one` |

### トークンを推定しない

`usage` を返さないプロバイダがある（OpenAI互換を名乗るローカルサーバに多い）。
そこで文字数から推定すると、**根拠のない数字が「計測値」として並ぶ**。
取れないときは `missing_usage` を数えて「未報告」と出す。0 も作らない
（「計測していない」と「0だった」は別物）。

計測より前に走った実行は `elapsed_ms` を持たない。画面はその場合だけ
従来の等分表示に落とす（`RunDetail.TraceView` の `hasTiming`）。

### スレッドローカルだけにしなかった理由

実行ごとの隔離はスレッドローカルで足りる（実行1件＝1スレッド）。だが
レビュアーを `ThreadPoolExecutor` で並列化すると、ワーカーからは親の
スレッドローカルが見えず、**そのぶんが黙って0になる**。数字は出ているのに
実態と違う、という最悪の壊れ方なので、集計器はロック付きの普通の
オブジェクトにし、ワーカー側は `metrics.use_collector(parent)` で明示的に
受け取る。忘れたときにどうなるかは
`TestThreadSafety.test_引き継がないと落ちる_これが並列化のときの罠` が固定している。

### なぜ合計を別列（`executions.metrics`）に持つか

per-node は trace に入るので、そこから足せば列は要らない。だが実行履歴の
一覧に合計を出すには一覧クエリで trace を読むことになり、
「一覧から `history`/`trace` を落として転送量を減らす」という予定と
正面からぶつかる。合計だけ別列に持てば、一覧は trace を読まずに済む。

実行**中**の合計は、画面が届いた trace から足す（`lib/cost.totalsOf`）。
保存済みの列はポーリング間隔ぶん遅れるため。終了後は両者が一致する。

### 表示

| 場所 | 何を出すか |
|---|---|
| 実行詳細の左ペイン | 合計・LLM待ちの割合・呼び出し回数（`.cost-summary`） |
| 実行詳細のトレース | ノード別の内訳表＋**実時間に比例した帯** |
| 実行履歴の一覧 | 「所要」「トークン」列（`executions.metrics` から） |
| `verify_run.py` | ノード別の表＋合計。全角の桁ずれは `_width` で補正 |
| Streamlit 版 | `trace_view.trace_rows` に「所要・トークン」列 |
