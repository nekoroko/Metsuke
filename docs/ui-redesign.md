# GUI更新要領 — サイドバーナビゲーションへの移行

> **状態: 実装済み**（案A・全4段階を適用）。以下は移行時の設計判断の記録。

## 1. 目的

現在のUIは `st.tabs` による6枚のフラットなタブ構成で、アプリの機能領域が
画面構造に表れていない。「ツール作成」「ライブラリ」「エージェント」は
本来ひとつの領域だが、「スケジュール」「実行履歴」と同列に並んでいる。

本アプリの機能は次の3領域に整理できる。この構造をそのまま画面に出す。

| 領域 | 含まれる機能 |
|---|---|
| ツール管理 | ツール作成 / ライブラリ / エージェント |
| スケジュール | スケジュール指定 |
| 実行管理 | 実行履歴 |

「作成時のプレビュー実行」「ライブラリからの手動実行」も実行ではあるが、
これらは各操作の文脈に埋め込まれているものなので、ナビゲーションには出さない。

## 2. 情報設計

```
┌─ サイドバー ────────────┐
│  ⚡ AI Agent Studio      │
│  🖥️ ローカルLLM          │   ← 接続中プロバイダの表示
│                          │
│  ツール管理              │   ← セクション見出し
│    ✨ 作成               │
│    📦 ライブラリ         │
│    🧠 エージェント       │
│                          │
│  スケジュール            │
│    🕐 スケジュール       │
│                          │
│  実行管理                │
│    📋 実行履歴           │
│                          │
│  ─────────────           │
│    ⚙️ 設定               │   ← 領域横断のため独立
└──────────────────────────┘
```

サイドバーの並び順は「ツール管理 → スケジュール → 実行管理」とする。
これは上下関係（階層）ではなく、**ツールを作る → 動かす時期を決める →
動いた結果を見る**という利用順序を表す並びである。

「設定」は3領域のいずれにも属さない横断的な機能なので、区切りを入れて
最下部に単独で配置する。

### 2.1 決めが必要な点: ツール管理の3画面をどう出すか

| 案 | 見え方 | 評価 |
|---|---|---|
| **A. サイドバーのサブ項目**（推奨） | 「ツール管理」は見出しとして表示され、その下に3項目が並ぶ。項目を直接クリックして遷移 | 1クリックで目的の画面に着く。URLも画面ごとに分かれる。「ツール管理」自体はクリックできない |
| B. サイドバー1項目＋画面内タブ | サイドバーは「ツール管理」1項目。開いた先の画面上部にタブが3枚 | 「ツール管理」というまとまりが強く出る。目的の画面まで2クリック。URLは1つ |

**A を推奨する。** 「サイドバーに各構造を配置する」という要件に素直であり、
Streamlitの `st.navigation` がセクション付きサイドバーを標準で描画できるため
追加のCSSも不要。B が必要なら「ツール管理」の概要画面を1枚追加する形になる。

## 3. 実装方式

`st.navigation` + `st.Page` を使う。**Streamlit 1.60.0 で動作確認済み**
（セクション付きdict、callableページ、Materialアイコン、`url_path` 指定）。

```python
nav = st.navigation({
    "ツール管理": [
        st.Page(page_create,  title="作成",         icon=":material/add:", default=True),
        st.Page(page_library, title="ライブラリ",   icon=":material/inventory_2:"),
        st.Page(page_agent,   title="エージェント", icon=":material/smart_toy:"),
    ],
    "スケジュール": [st.Page(page_schedule, title="スケジュール", icon=":material/schedule:")],
    "実行管理":     [st.Page(page_history,  title="実行履歴",     icon=":material/history:")],
    "":             [st.Page(page_settings, title="設定",         icon=":material/settings:")],
})
nav.run()
```

- ページはファイルではなく **callable（関数）** で登録する。共通部品を
  普通の `import` で共有でき、ファイル分割の粒度を自由に決められるため。
- アイコンは絵文字ではなく **Materialアイコン**（`:material/xxx:`）を使う。
  絵文字はOS・ブラウザで見た目が変わるため、統一感を出すのに向かない。
- `st.navigation` は Streamlit **1.36以降**。`requirements.txt` の
  `streamlit>=1.29` を `>=1.36` に引き上げる。

### 3.1 副次的な効果: 無駄な処理が減る

現在は `st.tabs` を使っているため、**どのタブを見ていても6タブ分の中身が
毎回実行される**。特に設定タブは `sandbox_image_status()` を毎回呼んでおり、
これは `podman image inspect` のプロセス起動を伴う。つまり画面上の何を操作しても
毎回podmanが呼ばれている状態にある。

`st.navigation` では選択中のページしか実行されないため、この呼び出しは
設定画面を開いているときだけになる。

## 4. ファイル構成

`app.py` は現在1209行あり、6画面ぶんの実装が1ファイルに同居している。
ナビゲーション移行にあわせて分割する。

```
app.py                  エントリ。init_db / スケジューラ起動 / CSS注入 /
                        ナビゲーション定義のみ（100行程度）
ui/
  __init__.py
  common.py             CSS、バッジ、preview_options、preview_and_fix、
                        verified_profile_caption 等の共通部品
  page_create.py        ツール作成
  page_library.py       ライブラリ
  page_agent.py         エージェント
  page_schedule.py      スケジュール
  page_history.py       実行履歴
  page_settings.py      設定
```

各 `page_*.py` は `def render():` を1つ公開し、`app.py` がそれを
`st.Page` に渡す。

`st.set_page_config` / CSS注入 / `init_db()` / スケジューラ起動は
`app.py` に置く。エントリスクリプトは毎回のリランで先頭から実行されるため、
全ページに共通で適用される。

## 5. 各画面の構成

### 5.1 共通ヘッダー

現在ページ最上部にある `st.title` と接続プロバイダのキャプションは
**サイドバーへ移す**。本文領域は各画面の内容だけにして、縦方向の情報量を稼ぐ。

各画面の先頭には、その画面が何をするところかの1行説明を置く。

### 5.2 作成

現状維持。ツール／エージェントの切り替えラジオは、画面が分かれた後も
「作成」画面の中に残す（作るものの種類の選択であり、機能領域ではないため）。

### 5.3 ライブラリ / エージェント / 実行履歴

前回のコミットでカード化済み。構成は変えない。
件数が増えた場合に備え、**検索ボックスと状態フィルタ**（検証済み／下書き）を
一覧の上部に追加する。

### 5.4 スケジュール

現状維持。

### 5.5 設定

現在1画面に「LLMプロバイダ」「Thinking」「接続テスト」「検索プロバイダ」
「ツール実行時ライブラリ」「サンドボックスのファイルアクセス」が縦に並んでおり、
400行超の長大な画面になっている。**画面内タブで分類する。**

| タブ | 内容 |
|---|---|
| LLM | プロバイダ設定、Thinking設定、接続テスト |
| 検索 | 検索プロバイダとAPIキー |
| サンドボックス | ツール実行時ライブラリ、イメージ状態、追加マウント |

## 6. 移行手順

1コミットずつ独立して検証・巻き戻しできるように4段階に分ける。

| 段階 | 内容 | 振る舞いの変化 |
|---|---|---|
| 1 | `ui/common.py` を切り出し。CSS・バッジ・プレビュー関連を移動 | なし |
| 2 | 各タブの中身を `ui/page_*.py` の `render()` へ移動。`app.py` は `st.tabs` のまま各 `render()` を呼ぶ | なし |
| 3 | `st.tabs` を `st.navigation` に置換。ヘッダーをサイドバーへ移動 | ナビゲーションが変わる |
| 4 | 設定画面のタブ分割、一覧の検索・フィルタ追加 | 各画面の中身が変わる |

段階1〜2は純粋な移動なので、差分は大きいが挙動は変わらない。
実際に見た目が変わるのは段階3以降。

## 7. 影響範囲とリスク

| 項目 | 内容 | 対応 |
|---|---|---|
| Streamlitのバージョン | `st.navigation` は1.36以降 | `requirements.txt` を `>=1.36` に引き上げ |
| session_stateのキー | `tc_{id}` 等の動的キーはそのまま使える。画面をまたいでも保持される | 変更不要 |
| ページ間の状態 | 「作成」で生成したコードは `st.session_state["generated"]` に入る。画面を移動しても消えない | 変更不要。ただし作成画面を離れて戻ったときの表示を要確認 |
| ブラウザのURL | 画面ごとにパスが割り当てられる | ブックマーク可能になる（改善） |
| 移動時の事故 | 1209行の移動で `with tab_x:` のインデントを外すため、取りこぼしが起きうる | 段階1〜2の完了時点でAppTestによる全画面の描画確認を行う |

## 8. 検証方法

Streamlit公式の `st.testing.v1.AppTest` を使い、ヘッドレスで確認する
（前回のGUI変更でも使用し、実際に不具合を検出できている）。

- 全ページの初期描画で例外が出ないこと
- 各ページのウィジェット（ボタン・入力欄）が期待どおり存在すること
- 設定の保存が実際にDBへ反映されること（入力→保存→読み出しの往復）
- 未検証ツールの「実行」ボタンが無効であること

**AppTestで確認できるのはDOMの構造までで、配色・余白・全体の印象は
確認できない。** 見た目の最終判断は実際に起動して行う必要がある。
