# 回答精度の改善要領 — 数値の取り違えと情報の取りこぼしを防ぐ

## 0. きっかけ

「SKハイニックスの最新の株価動向と業績」の実行結果（exec ID `ecc0bed2`, 2026-07-29）で、
次の3つの欠陥が同時に出た。原因はそれぞれ異なる。

| 欠陥 | 内容 | DONE時点で出典が見えていたか | 原因 |
|---|---|---|---|
| A. 単位の取り違え | 検索結果の「売上高約**83兆ウォン**（約9兆円）」を、回答では「売上高約**9兆ウォン**（約9兆円）」と記述。ウォンの値を円の値で置き換えており、約9倍ずれている | **見えていた** | 転記失敗 |
| B. 値動きの欠落 | 検索結果にあった `-7.47%`（SKHY 07/27終値）に一切触れず、値動きを「関心は極めて高く推移」とだけ記述 | **見えていなかった** | 履歴トリミング |
| C. 値動きの欠落2 | 検索結果にあった `-8.34%`（000660.KS 7/24）にも触れていない | **見えていた** | 注意の失敗 |

さらに、Aによって回答は単体で破綻している。第2四半期の**予想**売上高を「約9兆ウォン」、
第1四半期の**実績**売上高を「52兆5763億ウォン」と書いた上で「過去最高益更新の見込み」と
結論しており、予想が実績の1/6になっている。

### 0.1 なぜLLMによる検証では止まらないのか

この結果を Sonnet 5 にファクトチェックさせたところ、**欠陥Aを検出できなかっただけでなく、
「Q2の売上約83兆ウォン・営業利益約64兆ウォンをアナリストコンセンサスとして扱っており正確」
と、逆に正しいと判定した。** レポートに書かれていない値（83兆ウォン）を、レポートの記述
として読み替えている。

- 回答を書いた側（ローカルLLM）: 83兆ウォン → 9兆ウォン に誤変換
- 検証した側（Sonnet 5）: 9兆ウォン → 83兆ウォン に誤復元

**両方向に、独立に、同じ種類の誤り（文脈的にありそうな数値への無意識な正規化）が起きている。**
数値照合の最終防衛線をLLMに置く設計は成立しない、という前提で以下を組む。

なお本アプリの `reviewers.py` の fact_checker は `history[-10:]`（600文字/件）を見るため、
`-7.47%` も `83兆ウォン` も視野に入った上でOKを返している。プロンプトの追記だけでは
主防御にならないことが実測で確認できている。

```python
    """
    日付表現と、その前後40文字の文脈を返す。
    「29日に第2四半期決算の発表を控える」のような予定を拾うために使う。
    """

def normalize(entry: dict) -> tuple:
    """比較用のキー。(丸めた値, 単位) を返す"""

def find_conversion_pairs(text: str) -> list[dict]:
    """
    「A単位1（約B単位2）」の換算ペアを抽出する。
      例: 「83兆ウォン（約9兆円）」→ {"src": 8.3e13, "src_unit": "ウォン",
```

## 3. `numeric_checker`（新規レビュアー）

`reviewers.py` に追加する。**LLMを一切呼ばない**。他のレビュアーと戻り値の形だけ揃える。

### 3.1 チェックA: 換算ペアの整合（高信頼）

`find_conversion_pairs()` で得た各ペアについて:

- 単位が同一（`X円（約Y円）`）→ 値が一致しない場合 NG
- 単位が異なる → 通貨ペアごとの許容レンジ内か検査

```python
# 為替は動くため、桁の取り違えだけを捉えられる広いレンジにする。
# 狭くすると為替変動で誤検出が出て、レビューが信用されなくなる。
CONVERSION_BANDS = {
    ("ウォン", "円"): (0.03, 0.30),
    ("ドル", "円"):   (50.0, 400.0),
    ("円", "ドル"):   (1/400, 1/50),
}
```

今回の事例:
- `83兆ウォン（約9兆円）` → 比率 0.108 → レンジ内 → OK
- `9兆ウォン（約9兆円）` → 比率 **1.0** → レンジ外 → **NG**

**このチェック単体で欠陥Aを確実に止められる。**

### 3.2 チェックB: 未照合の数値

回答中の単位付き数値が、実行履歴のどこにも現れない場合に指摘する。

照合の緩和（誤検出を減らすため）:
- 単位が一致していること
- 完全一致、または**丸めの一致**（回答「約84兆ウォン」／履歴「84兆1693億ウォン」は
  上位2桁が一致するので照合成立とみなす）
- 回答が履歴の値から**四則演算で導ける**場合は判定不能なので、指摘はするが
  NEEDS_REVISION の根拠にはしない（後述の verdict 方針）

今回の事例では `9兆ウォン` と `7兆ウォン` が履歴に存在せず、2件とも真陽性になる。

### 3.2.1 プロトタイプによる事前検証（実施済み）

上記の抽出・判定ロジックを実データで試行し、想定どおり動くことを確認済み。

```
=== 換算ペア検査 ===
  [検索結果] 83兆ウォン（約9兆円）   比率=0.108  OK
  [検索結果] 64兆ウォン（約7兆円）   比率=0.109  OK
  [回答]     9兆ウォン（約9兆円）    比率=1.000  ★NG★
  [回答]     7兆ウォン（約7兆円）    比率=1.000  ★NG★

=== 数値抽出 ===
  [Q1実績] [('52兆5763億ウォン', 'ウォン'), ('37兆6103億ウォン', 'ウォン')]  ← 複合表記OK
  [moomoo] [('-7.47%', '%')]                                          ← 符号付きOK
  [日付]   []                                                          ← 日付は除外OK

=== 未照合検出（回答 vs 検索結果） ===
  9兆ウォン  -> ★履歴に存在しない★
  9兆円      -> 照合OK
  7兆ウォン  -> ★履歴に存在しない★
  7兆円      -> 照合OK
```

チェックAとチェックBが**独立に**欠陥Aを捕捉している。片方の判定基準を
将来緩めても、もう一方が残る。

### 3.3 verdict の方針

| 条件 | verdict |
|---|---|
| チェックAで違反あり | `NEEDS_REVISION` |
| チェックBで未照合が1件以上 | `NEEDS_REVISION` |
| 上記なし | `OK`（issuesが空でも返す） |

差し戻しは `max_critiques = 2` で上限が掛かっているため、暴走しない。

### 3.4 実装

```python
def numeric_checker(output: str, history: list = None) -> dict:
    """
    回答中の数値を実行履歴と機械的に突き合わせる。LLMは使わない。

    LLMによる数値検証は、書く側・検証する側の双方で
    「文脈的にありそうな数値への無意識な正規化」が起きるため信用できない
    （docs/accuracy-improvements.md 0.1 参照）。ここは決定的な処理で担保する。
    """
    issues = []

    for pair in find_conversion_pairs(output):
        if not _conversion_plausible(pair):
            issues.append(
                f"換算が矛盾しています: 「{pair['raw']}」。"
                f"{pair['src_unit']}と{pair['dst_unit']}の比率が想定から外れています。"
                f"検索結果の値をそのまま書き写しているか確認してください。"
            )

    hist_text = "\n".join(e.get("content", "") for e in (history or [])
                          if e.get("role") == "result")
    hist_keys = {normalize(n) for n in extract_numbers(hist_text)}
    for n in extract_numbers(output):
        if not _matches_any(n, hist_keys):
            issues.append(
                f"「{n['raw']}」は実行履歴の検索結果に見当たりません。"
                f"出典の数値をそのまま書き写すか、この数値を削除してください。"
                f"（該当箇所: …{n['context']}…）"
            )

    return {
        "reviewer": "numeric_checker",
        "verdict": "NEEDS_REVISION" if issues else "OK",
        "issues": issues,
        "instruction": (
            "指摘された数値を、実行履歴の検索結果に書かれている値そのものに直してください。"
            "単位（ウォン／円／億／兆）を変換しないこと。"
            "換算値を書く場合は、元の値を主として書き、換算は括弧内に留めること。"
        ) if issues else "",
        "raw": "",
    }
```

## 4. 数値台帳（findings ledger）

### 4.1 なぜ必要か

欠陥B（`-7.47%` の欠落）は、DONE を書く時点で `graph.py:268` の
`history[-(MAX_HISTORY_ROUNDS * 2):]` により**出典が窓の外に落ちていた**。
プロンプトをどれだけ強化しても、見えていないものは書けない。

### 4.2 状態の追加

`state.py`:

```python
class AgentState(TypedDict):
    ...
    findings: list[dict]   # 検索結果から抽出した数値・日付。履歴トリミングの対象外
```

`make_initial_state()` に `"findings": []` を追加する。
（初期状態の生成は既に1箇所へ集約済みなので、追加漏れは起きない）

### 4.3 蓄積

`graph.py` の `react_step`、ツール実行の分岐で result を得た直後:

```python
new_findings = state.get("findings", []) + collect_findings(
    result, tool_name=tool_name, query=action["arg"], step=state["step_count"]
)
```

`collect_findings()` は `numeric.py` の `extract_numbers` / `extract_dates` を使い、
1件を次の形にする。

```python
{"kind": "number", "raw": "-7.47%", "context": "終値 07/27 16:00 ET",
 "source": "web_search(SKハイニックス 株価)", "step": 2}
{"kind": "date",   "raw": "29日",   "context": "29日に第2四半期決算の発表を控える",
 "source": "web_search(SKハイニックス 決算)", "step": 3}
```

上限は40件。`(raw, context先頭20文字)` で重複を除き、超過したら古い順に捨てる。

### 4.4 プロンプトへの提示

`build_system_prompt(step_count, max_steps, reasoning_detected, findings)` に引数を追加し、
次の節を挿入する。

```
## これまでに取得した数値・日付
以下は、これまでの検索結果から機械的に抽出したものです。
出典の原文そのままなので、回答に書くときはこの表記を変えないでください。

- -7.47%（終値 07/27 16:00 ET）… web_search(SKハイニックス 株価) / Step 2
- 83兆ウォン（コンセンサスは売上高約83兆ウォン（約9兆円））… web_search(SKハイニックス 決算) / Step 3
- 29日（29日に第2四半期決算の発表を控える）… web_search(SKハイニックス 決算) / Step 3
...
```

数値と短い文脈だけなので、40件でも数百トークンに収まる。

### 4.5 DONE前の点検要求

同じくシステムプロンプトの `## 回答形式` の直後に追加する。

```
## DONEを出す前の点検
「これまでに取得した数値・日付」の一覧を上から1件ずつ確認し、
タスクの問いに関係するものを回答に含めたか点検してください。
特に、増減率・価格・日付など、結論の向きを左右する数値を

関係がないと判断して省く場合は、それが妥当か一度考えてから省くこと。

無いか必ず確認すること。
```

欠陥Bの直接の対策であると同時に、Cにも効く。

## 5. システムプロンプトへの追記

`graph.py` の `build_system_prompt` 内、`## 表記ルール` に追加する。

### 5.1 単位の書き写し（欠陥A）

```
- **検索結果の数値は、単位を変換せずそのまま書き写すこと。**
  「83兆ウォン（約9兆円）」と書かれていたら、「83兆ウォン（約9兆円）」と書く。
  ウォンの位置に円の値を入れてはいけない。
- 換算値は括弧内の補助にとどめ、主となる値は必ず出典の単位のまま書くこと。
- 「A単位（約B別単位）」の形で書いたら、AとBの桁が妥当か一度確認すること。
  ウォンと円はおおよそ10倍程度の差があり、同じ値になることはない。
```

### 5.2 予定日の注記

```
- 検索結果に「◯日に発表」等の予定が含まれており、その日が今日以前、
  または数日以内である場合、予想値を書くときに
  「◯日発表予定のため未確定」と必ず注記すること。
```

今回、7/29未明の実行で「29日に第2四半期決算の発表を控える」を取得していながら、
注記なしで予想値を結論として提示していた。

## 6. `fact_checker` の強化

`reviewers.py` の `FACT_CHECKER_PROMPT` にチェック観点を追加する。
`numeric_checker` と二重化するが、機械チェックが拾えない
「文脈上の重要度」の判断はLLM側に残す。

```
7. **結論の向きを変える数値の欠落**: 実行履歴に、下落率・減益・赤字・遅延など、
   最終回答の結論と逆向きの数値や事実が含まれていないか確認してください。
   含まれているのに最終回答が触れていない場合は、必ず NEEDS_REVISION とし、
   どの数値を反映すべきか明示してください。
8. **数値の書き写し**: 最終回答の数値が、実行履歴の検索結果に現れる値と
   一致しているか確認してください。特に単位（ウォン／円／億／兆）が
   入れ替わっていないかを見てください。
```

あわせて、`fact_checker()` に `findings` を渡し、
プロンプトの `## エージェントの実行履歴（抜粋）` の前に台帳を提示する。
履歴は600文字で切られるが、台帳は切られないため、
レビュアー側でも取りこぼしの検出精度が上がる。

## 8. 検証方法

### 8.1 `numeric.py` の単体テスト

抽出と換算判定の境界を固定する。LLM不要で決定的に回せる。

| 入力 | 期待 |
|---|---|
| `83兆ウォン（約9兆円）` | 換算ペア成立、比率0.108 → OK |
| `9兆ウォン（約9兆円）` | 換算ペア成立、比率1.0 → **NG** |
| `52兆5763億ウォン` | 複合表記を1件として抽出、値 5.25763e13 |
| `-7.47%` | 符号付きで抽出 |
| `2026年7月29日` | 数値としては抽出せず、日付として抽出 |
| `1,919,000` | 単位が無いので数値としては抽出しない |

### 8.2 実データによる回帰テスト（LLM不要）

**今回の実行（exec ID `ecc0bed2`）の history と最終回答をそのまま
フィクスチャとして保存する。** DBの `executions.history` から取得できる。

```python
def test_numeric_checker_catches_unit_error():
```

# 第2部: 出典の要約と訂正チェック（グラフ変更）

## 11. `digest` ノード — 出典を取得して使える形にする

### 11.1 なぜ必要か

現在エージェントが見ているのは `web_search` が返す**200〜250文字のスニペット**だけである。
実測では次のように数値の途中で切れていた。

```
第1四半期の売上高52兆5763億ウォン、営業利益37兆6103億ウォ   ← 切断
```

システムプロンプトは「スニペットだけで数値が読み取れない場合は fetch_url で本文を
取得すること」と指示しているが、**観測された実行では fetch_url が一度も呼ばれなかった**。
8B〜12B級のモデルに自発的な深掘りを期待する設計は成立していない。
そのため、グラフ側で強制する。

### 11.2 最重要の注意: 要約に数値を通してはいけない

出典をLLMで要約すると、**欠陥Aと同じ「ありそうな値への正規化」が要約時点で起きる**。
しかも要約結果は以降「出典の内容」として扱われるため、誤りが確定してしまう。
検証の土台が汚染されるので、素のスニペットを使うより悪化しうる。

したがって digest は**二層構造**にする。

| 層 | 生成方法 | 担当 |
|---|---|---|
| `facts` | `numeric.py` による機械抽出（**LLMを通さない**） | 数値・日付 |
| `summary` | LLMによる要約 | 定性的な文脈のみ |

要約プロンプトでは**数値を書かせない**。「数値には触れず、何についての記事かを
150文字程度で述べよ」と指示する。数値は必ず `facts` 側の原文表記を使わせる。

これにより「要約はLLM、数値は原文」という分担になり、要約が壊れても数値は壊れない。

### 11.3 状態の追加

`state.py` に追加する。

```
findings: list[dict]     # 第1部 §4 の数値台帳
sources: list[dict]      # digest 結果。トリミング対象外
digest_count: int
max_digests: int
```

`sources` の1件は次の形にする。

```
{"url":     "https://finance.biggo.jp/news/...",
 "title":   "SKハイニックス、29日に2Q決算発表へ",
 "summary": "AIメモリー需要を背景に四半期最高益更新の見方を伝える記事。",  # LLM生成・数値なし
 "facts":   [{"raw": "83兆ウォン", "context": "コンセンサスは売上高約83兆ウォン（約9兆円）"},
             {"raw": "29日", "kind": "date", "context": "29日に第2四半期決算の発表を控える"}],
 "status":  "ok"}        # ok | fetch_failed | no_numbers
```

### 11.4 HTMLからテキストへ

`beautifulsoup4` はサンドボックスイメージ側にしか無く、ホストでは使えない。
標準ライブラリの `html.parser` で足りることをプロトタイプで確認済み。

```
class _TextExtractor(HTMLParser):
    SKIP = {"script", "style", "noscript", "head", "svg"}
```

検証結果:

```
入力: <script>var x="9兆ウォン";</script> を含むHTML
出力: script/style の中身は混入せず、本文のみ
数値: ['83兆ウォン', '9兆円', '64兆ウォン', '7兆円', '650％']
換算: 83兆ウォン（約9兆円）=0.108 OK / 64兆ウォン（約7兆円）=0.109 OK
```

あわせて `tools.fetch_url` を改修する。

- タグ除去後のテキストを返す（現状は生HTMLを `[:3000]`）
- 上限を 3000 → 8000 文字（タグが消えるぶん実質的な情報量は増える）

### 11.5 ノードの動作

1. 直前の result から URL を抽出する（`https?://\S+`）
2. **先頭1件のみ**取得する。検索結果3件すべてを digest すると
   1検索あたり3回のLLM呼び出しになり、実行時間が破綻する
3. `fetch_url` → `html_to_text` → 8000文字
4. `numeric.py` で `facts` を機械抽出し、数値台帳（`findings`）にも合流させる
5. LLMで `summary` を生成する（**数値に触れない**指示）
6. `sources` に積む

予算は `digest_count` で別管理する。`step_count` はエージェントの「行動選択回数」で
あり、内部処理をそこに数えないという既存の方針（`tool_verify_count`）に合わせる。

取得に失敗した場合、または本文から数値が1件も取れなかった場合（JS描画サイト）は
`status` に記録して次へ進む。**digest の失敗でループを止めない。**

### 11.6 予算

| 項目 | 既定値 | 根拠 |
|---|---|---|
| `max_digests` | 3 | 1件あたり fetch 約2秒 + LLM約25秒。3件で **+80秒程度** |
| 取得するURL | 検索結果の先頭1件 | 3件取ると1検索で+75秒になり非現実的 |
| 本文の上限 | 8000文字 | 要約は履歴を持たない単独呼び出しなので、Context 4096 でも収まる |

観測された実行は5分42秒だった。digest 3件で **+80秒程度**の増加に収まる見込み。

## 12. `correct` ノード — 訂正チェックをグラフに組み込む

### 12.1 位置づけ

`critic`（LLMによる品質レビュー）とは分ける。

| | `correct` | `critic` |
|---|---|---|
| 判定 | 機械（決定的） | LLM |
| 対象 | 数値の転記・換算・取りこぼし | 論理・網羅性・表現 |
| コスト | LLM 0回 | 1〜3回 |
| 実行順 | **critic より前** | correct の後 |

先に数値を直してから内容レビューに入る。順序が逆だと、critic が誤った数値を
前提に指摘を組み立ててしまう。

### 12.2 グラフ

```
                    ┌─ tool（検索系） → digest → verify_tool ─┐
react ──────────────┼─ tool（その他） ───────────────────────┼──→ react
                    ├─ code ─────────────────────────────────┘
                    │
                    └─ DONE → correct ─┬─ 訂正あり ──→ react
                                        └─ 訂正なし ──→ critic ─┬─ 要修正 → react
                                                                  └─ OK    → END
```

`digest` を `verify_tool` の前に置く理由: verify_tool は「検索結果がクエリの意図に
答えているか」を判定するが、スニペットだけで判定するより digest 後の方が材料が良い。

### 12.3 correct ノードの処理

1. `correction_count >= max_corrections` なら素通しして critic へ
2. `max_steps - step_count <= 1` なら差し戻す予算が無いので critic へ
3. 履歴から DONE 本文を取り出し、`numeric_checker` に
   `history` / `sources` / `findings` を渡して機械チェックする
4. `OK` なら critic へ
5. 問題があれば「（自動訂正チェック）」で始まるフィードバックを履歴に積み、
   `status = "running"` で react へ戻す

`status` の使い分けに注意する。既存の `route_after_react` は `needs_revision` を
「critic へ」の意味で使っている。`correct` からの遷移もこれに合わせ、
**訂正が必要なときだけ `running`** にして react へ戻す。

### 12.4 ルーティングの変更

- `route_after_react` の `needs_revision` の遷移先を `"critic"` → `"correct"` に変更
- `route_after_correct` を新設（`running` → react、それ以外 → critic）
- `route_after_digest` を新設（→ verify_tool）
- `workflow.add_node` を2つ追加し、`add_conditional_edges` の遷移先辞書を更新

### 12.5 ループしないことの担保

| 上限 | 値 | 効果 |
|---|---|---|
| `max_corrections` | 2 | 訂正の差し戻しは最大2回 |
| `max_steps` 残り | ≦1 で打ち切り | 差し戻す予算が無ければ critic へ素通し |
| `max_critiques` | 2（既存） | critic 側の差し戻しも従来どおり上限あり |

最悪ケースでも `react` の追加実行は 2（correct）+ 2（critic）= 4回で、
`max_steps = 10` の範囲に収まる。

## 13. `numeric_checker` の拡張（出典照合）

第1部 §3 のチェッカーに第3のチェックを足す。

**チェックC: 出典本文との照合**

`sources[].facts` は出典本文から機械抽出した原文表記なので、
スニペットよりも照合の母集団として信頼できる。

| 回答中の数値の所在 | 判定 |
|---|---|
| `sources[].facts` に存在 | 照合済み（出典本文で確認） |
| 検索スニペットにのみ存在 | 照合済み。ただし「本文未確認」と注記 |
| どちらにも無い | 未照合として指摘 |

これにより指摘が「どこにも無い」から「**引用元Aの本文に無い**」に具体化し、
差し戻しの指示も具体的になる。

## 14. 設定

深い検証は実行時間と引き換えなので、切り替えられるようにする。

| 設定キー | 既定 | 内容 |
|---|---|---|
| `enable_source_digest` | `true` | `digest` ノードの有効化 |
| `max_digests` | `3` | 1実行あたりの digest 件数 |
| `enable_correction` | `true` | `correct` ノードの有効化 |

`correct` はLLM呼び出しが無いため、既定ONで実害がない。
`digest` は実行時間が増えるため、対話的に使う場合に件数を減らせるようにしておく。

そちらを参照すること。ここに別の順序表を置くと二重管理になるため置かない。

## 設計上の判断

### タグ欠落を常に差し戻さない

`[実績]/[予想]` が1つも付いていない場合に差し戻すのは、**取得済みの情報に
「予想」「コンセンサス」等が混ざっているときだけ**にした（`_forecast_in_context`）。
予想と実績の取り違えが起こりえないタスクでも書式だけのために1ラウンド
消えるのは、規範が防ごうとしている「無駄なループ」そのものになる。

### 予想判定は文単位で行う

`「SK하이닉스 -9.35% 하락. 매출 78조9680억원 전망.」` のように、1つの文脈に
実績と予想が同居する。文脈全体で「予想」を判定すると、隣の文の「전망」に
引きずられて実績の下落率まで予想と誤判定した（実測で発生）。
`numeric.sentence_containing` で、その数値が入っている文だけを見る。
半角ピリオドは小数点と紛れるため、前後が数字でないときだけ文の区切りとみなす。

### critic は予算切れでも走らせる

以前は残りステップが1以下だと critic 自体をスキップしていた。
これは「最後に出力される＝実際に読まれる回答こそ誰にもレビューされない」
という逆の構造だった。いまはレビューを行い、差し戻せない場合は指摘を
`verification_notes` へ移して最終回答の末尾に「（レビュー未反映）」として出す。
黙って古い版を確定させない。LLM呼び出しは最悪1回増えるが、
確定版が無検査で出るコストの方が高い。

### 符号チェックは率と額のペアに限る

「前日比 -3.2%、年初来 +12%」は正常なので、率同士の符号違いは見ない。
率（%）と通貨額の組で符号が逆のときだけ指摘する。

## 判断が要った点

### ラベル照合は「表のなれの果て」にだけ効かせる

事故のもとになった `41.74億売買代金0.55%売買回転率` は、区切りの無いフィールドの
羅列で、値の隣にラベルが来る。ここでは隣接位置からラベルを取れる。

一方、文章（`28日の終値は前日比-14.65%`）で同じことをすると、その値を「終値」と
呼んだだけで「前日比と違う」と判定してしまう。実際、統合実行で誤検出が出た。
`looks_tabular()` で、助詞も空白も無い文脈のときだけ隣接ラベルの一致を要求する。

加えて、回答のラベルが出典テキストに存在しない場合は「言い換え」とみなして
判定しない。出典に「配当利回り」があり、それが別の値に付いているときだけ
付け替えとして扱う。

### タスクの主語抽出

日本語のタスクは分かち書きされないため、空白分割では
「SKハイニックスの直近の決算と株価を調べて」が丸ごと1語になり、
補強クエリも関連性判定も壊れる。英数字・カタカナ・漢字2〜4字のかたまりを拾い、
隣接するものを繋いで主語を作る（`SK` + `ハイニックス` → `SKハイニックス`）。

### 実装しなかったこと

「compose の出力スキーマ自体に value_type 必須フィールドを設ける」（§7）は、
レポート本文をJSONで書かせることになり、過去に構造化出力を撤回した理由
（途中で切れたら全損・記述が痩せる、§0.2）に逆戻りする。
代わりに**台帳側**に型を持たせ、本文のタグはそれと機械照合する形にした。
型の正は台帳であって、モデルの判断ではない。

# doc26 / doc27 の指摘に対する調査と修正（2026-07-29）

## 1. 1ラベル・複数値の扱い

`label_value_mismatches` は元々「そのラベルの出現ごと」に独立して見ており、
代表値を1つに決め打ちしてはいなかった。ただし2つの穴があった。

- **「約」がラベルとして採られていた。** 「約650%」の直前が「約」なので、
  文書内に何度も出る「約」が別々の値と結び付いた。`_LABEL_MODIFIERS` で
  数量修飾語（約・およそ・ほぼ・推定・合計…）をラベルから外した。
- **抽出漏れを「出典に無い」と断じていた。** 数値の途中に改行が入る等で
  出典側の抽出が失敗すると、原文に確かにある値が捏造として却下される。
  `appears_verbatim`（カンマ・空白を無視した原文照合）を通過条件に追加した。

さらに、原文でラベルと値が隣り合っていれば正しい組とみなす `cooccurs` を
追加した。窓は12文字。広く取ると同じ段落に別の指標があるだけで何でも通る。

**連結を跨いだ誤判定に注意。** 実装中、複数のテキストを1本に連結して探すと、
前のページの末尾と次のページの先頭が隣り合って「近い」と誤判定した。
テキストは1件ずつ見る（`_as_texts`）。

## 2. 表形式は距離ではなく「隣接順序」で判定する

`…売買代金0.55%売買回転率配当利回り--…` では、正しいラベル（売買回転率）の
すぐ後ろに別のラベル（配当利回り）が続く。距離で見ると両方「近い」ので、
付け替えを見逃す。表形式（区切りも助詞も無い）と判定した場合は、
`_adjacent_label` で「値の直前なら末尾、直後なら先頭」に来ているかを見る。

## 3. 置換候補の絞り込み

`candidates_for` は元々「単位が同じ」だけで絞っていた。桁とラベルを追加した。

- 単位が同じ（ウォンとウォン、%と%）
- 桁が1000倍以内（兆ウォンの利益に、数十万ウォンの株価を出さない）
- ラベルが一致するものを先頭に出す

なお、doc26で見えた無関係な候補の並びは、`correct` が差し戻しに添える
**台帳ダンプ**（取得済みの数値の一覧）である可能性が高い。こちらは
単位でも桁でも絞っていない。台帳は「見落とし防止」が目的なので絞らないが、
候補提示と混ざって読めるため、文言で役割を分けている。

## 4. compose 枠の会計が間違っていた（doc27の主因）

`critic <= compose - 1` は**correct が compose 枠を消費しない前提**でしか
成立しない不変条件だった。実際には compose 枠を消費するのは3者ある。

```
compose 枠 = 初稿1回 + correct の差し戻し + critic の差し戻し
```

`max_composes=3, max_corrections=2, max_critiques=2` では最大5回必要になり、
correct が先に使い切ると critic の指摘は必ず捨てられる。再現スクリプトで
`#12 correct → critic : レビュー: 要修正だが執筆枠が残っていない` を確認した。

修正は2段構え。

- `_enforce_budget_invariant` が `max_composes >= 1 + max_corrections + max_critiques`
  を保証する（リサーチは3→5）。
- `correct` は「残っている critic 回数ぶん」の compose 枠を予約し、
  そこへ食い込む差し戻しをしない（`reserve_compose_for_critic`）。

修正後の同じシナリオでは、critic が2回とも差し戻せている。

## 5. 確定済みフィールドは補記まで行う

検出だけで消えたままだったので、差し戻せない場合は
`append_missing_confirmed` が本文末尾に「検証済みだが本文に反映されなかった値」
として一覧を戻す。本文の文中へ差し込むのは機械にはできない（どの文のどこに
入れるべきかが決まらない）ため、追記にとどめる。

## 6. 本文の途中切断

`fetch_url` が文字数上限で切った場合、末尾に `…（本文はここで切れています）` を
付ける。検証側はこの印を見て、「出典に無い数値」の指摘に
「本文が途中で切れています。切れた先に書かれている可能性があります」を添える。
捏造と欠損は原因が違い、対処（再取得か削除か）も違う。

## 7. テストは実データの形で持つ

`tests/fixtures/noisy_sources.json` に、区切りの無い株価表・「約」が繰り返し
出る記事・途中切断・韓国語混在を、ノイズを含んだ形で置いた。
理想化したサンプルでは、この種の誤検出は原理的に再現しない。
実際のツール出力が手に入る場合は、このファイルへ raw のまま追加する。

## 追補: 指摘4件への対応（2026-07-29）

### ① 置換候補と参考リストを形式で分ける

同じ形式で並ぶと、絞り込んだ候補と絞っていない全件一覧の区別が付かない。

| 出どころ | 表示 | 絞り込み |
|---|---|---|
| `candidate_suggestion`（同じ項目名） | `【置換候補】…（出典で「営業利益」に付いている値）` | 単位・桁・項目名 |
| `candidate_suggestion`（項目名なし） | `【候補（参考）】…。単位と桁が近いだけで、同じ項目の値とは限りません` | 単位・桁 |
| 候補なし | `【置換候補なし】出典に「◯◯」の値は見当たりません` | — |
| `correct` の台帳ダンプ | `----` で囲った `【参考リスト】取得済みの数値（全件・絞り込みなし）` | なし |

さらに、**項目名が分かっているのに同じ項目名の値が無い場合は、単位と桁が近いだけの
値を候補に出さない**ようにした。doc26 で営業利益の候補に「世界のメモリ市場規模
1,500兆ウォン」が並んだのは、桁の帯（1000倍以内）だけでは別対象の値を弾けないため。

### ② 予算の式は「特殊解」だった

指摘のとおり、`max_composes >= 1 + max_corrections + max_critiques` は
**compose_count を増やす経路が3つしかない**という前提の上でしか成り立たない。
調べたところ4つ目があった。

- **空応答の再試行**（compose → compose）が compose_count を消費していた。
  上限は max_composes だけなので、空応答が続くと差し戻し用の枠を食い潰す。

`compose_retry_count` / `max_compose_retries` として別枠に切り出し、
上限に達したら correct へ抜けるようにした。式に含まれる消費者は次の3つに固定される。

```
compose_count を増やすのは:
  1. gap → compose（初稿）              : 1回
  2. correct → compose（数値の差し戻し） : 最大 max_corrections 回
  3. critic → compose（レビュー差し戻し）: 最大 max_critiques 回
（LLM例外で status=error になる経路も1回消費するが、そのまま END へ抜ける）
```

**指摘の件数は枠を増やさない**（1回の差し戻しで何件指摘しても消費は1つ）。
テストで、経路が増えたら落ちるようにしてある
（`test_compose_countを増やす箇所が増えていない`）。
また corrections × critiques の組み合わせを総当たりして、式が
最悪ケースを満たすことを確認している。

### ④ 表形式の判定境界

指摘のとおり、「助詞が無い」だけを条件にすると自然文へ及ぶ。実測すると、
`純利益9.2兆ウォン` `前年同期比650%増` `株価-14.65%` はいずれも
「表」と判定されていた。

条件を3つにした。

- 25文字以上
- 助詞・空白の密度が2%未満（ゼロを要求すると、実際の表にある
  「時価総額97,146,675,000千 KRW」の空白1つで弾かれる）
- 数字の並びが3つ以上（単位付きの数値ではなく数字の並びで数える。
  株数や売買代金は単位が離れた欄にある）

自然文10種と実物の表を並べた境界テスト（`TestTabularBoundary`）を入れた。
自然文側は全件 False、実物の表は True になる。
